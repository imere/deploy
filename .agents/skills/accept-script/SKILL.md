# 独立验收脚本

**实现方自己的测试不算验收。** 它可能为了通过而放宽断言，也可能测的是它自己写的 helper。
验收要另写一份脚本，只断言**可观测行为**。

## 1. 落点与形态

- 放临时目录（如 `.tmp/accept-<主题>.mjs`），**不入库** —— 它是一次性的证据，不是资产
- 直接 import **构建产物**（不是源码），这样验的是真正会被跑出去的东西
- 一组 `ok()` / `eq()` 断言，全部跑完打印计数；失败要**带上实际值**

## 2. 断言什么

- **契约**（返回码、退出码、输出分流：stdout vs stderr vs 日志）
- **边界**（歧义靠拒绝、缺省值从哪来、超限时报错而不是静默截断）
- **失败路径**（依赖注入一个会失败的实现，断言错误码与提示）
- **不留痕**（跑完之后目录里不该多出东西 —— 见「验收脚本自己不许弄脏机器」）

不要断言实现细节（内部调用了几次、用了哪个私有函数）—— 那会让重构变成改测试。

## 3. 先探明契约再写断言（实测踩过三次）

脚本自己写错前提比被测代码有 bug 更常见。写之前先用一次**探针脚本**确认：
- 这个函数是**抛错**还是**返回码**？
- 输出走 `write` 回调还是 stdout？
- 哪些参数是必填的？

实测教训：
- 断言「返回退出码 3」，而函数其实是**抛错**（退出码由顶层转换）→ 断言全错
- 断言「stderr 里有 X」，而错误被内部接住、信息在 stdout → 断言空
- 漏传必填参数导致报的错和要验的错不是同一个 → 误判成实现有问题

## 4. 验收脚本自己不许弄脏机器

实测：脚本里用默认依赖跑「真的落盘」那条断言，结果把发布目录写进了**真实用户目录**。
**验收不该在开发机上留痕。**

规则：
- 起临时目录，把「家目录 / 应用目录 / 状态目录」都指向它
- 或者干脆改断言：从「检查目录出现了」改成「检查输出里说了会写到哪」
- 跑完检查临时目录之外有没有多出东西

如果确实需要真跑：先看清默认路径是什么，跑完立刻清理并复查。

## 5. 与变异验证配套

验收脚本写完后做一轮 `mutation-verify`：撤掉修复 → 脚本也必须变红。
只有单测变红而验收脚本不变红，说明验收断言没打到点上。

## 6. 有些验收脚本不是一次性的 —— 判据

§1 说「一次性证据，不入库」，这条有个必须挑出来的例外。判据是**它验的东西会不会变**：

- 验「这次这个修复生效了吗」→ 留在临时目录，结论进了提交信息就没用了。
- 验「某个会持续变化的机制还在不在工作」→ 必须提升到常驻脚本并接进自动化。
  典型就是**门禁自检**：门禁脚本自己会被改，改完它是不是还在拦，只有再注入一次才知道。
  留在临时目录里，一是下次清目录就没了，二是「要定期重跑」变成靠人记 —— 等于没有。

实测：门禁注入自检写了 538 行、9 组注入全过，一开始按习惯留在 `.tmp/`，
而 `.tmp/` 在 `.gitignore` 里 —— 一份证明「门禁不是摆设」的资产，差点随着清目录一起消失。

提升时的检查清单（都是真踩过的）：

- **仓库根不能用相对路径拼**，要用 `import.meta.url` 推导。脚本从 `.tmp/` 挪到 `scripts/`
  只是换了一层目录，路径推导写死就会整份失效。
- **临时性注释必须清掉。**「本仓此刻有别的进程在编译同一仓库」这类描述当时是对的，
  进了常驻脚本就变成误导。改成不依赖当时状态的通用理由。
- **本机限制要写成通用表述**，不要写成「在我这台机器上」。
- **环境跑不了时要明说**（见下条），不能假绿。

## 7. 「环境不支持」在测试里与在门禁里处置不同

同一个事实（本机派生不了子进程）出现在两个语境，处置相反：

- **测试里**：检测 `spawnSync` 返回的 `r.error` 后 `t.skip()` 并写明原因。
  不检查 `r.error` 就会把环境问题报成断言失败，错误信息完全误导。
- **门禁自检里**：**不能 skip** —— 自检没跑成却显示绿，等于宣布一个没验过的结论。
  要单独归一类（例如「环境未生效」），退出码非 0，并把原因写清楚是环境而不是门禁瞎了。

共同点是**分类**：把「环境不支持」和「被测对象不对」分成两个桶。
混在一起会驱动人去改一个本来就对的东西。

## 8. 抽出纯函数之后，必须证明它**真接在判据上**

把内联判据抽成可测函数时，「抽象得漂亮」和「抽出来的东西在被使用」是两件事。
抽完但原处还留着一份（或者压根忘了改调用点），会得到一段**平行的死代码**：
它的测试全绿，门禁的行为与它无关。

验证只有一个办法 —— **注一个它理应抓到的错，看门禁是不是真的变红**：

- 选被抽函数里最容易整体失效的那个做锚点（例如让「找前置注释」恒返回 null），
  期望值是门禁大规模报缺而不是依然全绿。
- 注入点要在**抽出来的模块**里，而不是在原脚本 —— 打在原脚本上验的是别的东西。
- 还原后必须回到注入前的数字（不只是退出码回到 0 —— 缺口数、命中数要逐字一致）。

实测：让 `check-jsdoc-rules.mjs` 的 `docBefore` 恒返回 null，
`check-jsdoc.mjs` 从「465 符号 / 缺 0」变成「缺 465」、退出码 1；还原后回到「缺 0 / 18 疑似复述」。
同一手法用在 `check-imports`（层序整体倒置 → 报 88 处反向依赖）与
`dead-code`（引用计数恒为 0 → 报 345 处死代码）上也各自成立。

**注入要选能产生「干净的红」的那个。** 第一次把 `layerOf` 改成返回 99，
确实红了，但红在 `fmtEdge` 里 `LAYER_LABEL[…].slice` 的 TypeError ——
那是脚本本身对未知层号不健壮，不是「判据抓到了」。换成「合法层号但整体倒置」
才拿到干净的「反向依赖 88 处 / 结论：失败」。**红的理由不对，就不能算验证通过了。**
