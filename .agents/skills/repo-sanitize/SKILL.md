# 清痕与恢复

## 清痕 · Step 1 盘点什么算「公开处」

- **已被 git 跟踪的文件**（含历史里的每一个提交）
- 被忽略的本地目录不算，但要确认它真被忽略了：`git ls-files | grep '^<目录>/'` 有输出就是已经提交进去了

逐条 grep 这五类：绝对路径（仓库路径、主目录、全局 bin）、网络环境（代理地址端口）、凭据（`ghp_` / `github_pat_` / token / 密码）、机器标识（主机名、用户名）、处境描述。

**区分合成数据**：脱敏测试里的假 token 是测试数据不是泄露，别误删导致测试语义变化。

完整配方、替换表写法、复扫清单见 `references/sanitize-and-recovery.md`。

## Step 2 让本地目录退出版本控制

写进 `.gitignore` 后 `git rm -r --cached <目录>`。**只取消跟踪，不删文件**——那是本人要用的工作记忆。

## Step 3 备份（不可逆前必须有回滚点）

```bash
git bundle create .tmp/history-backup-<日期>.bundle --all
```

确认 bundle 真的生成了再进下一步。

## Step 4 重写历史

`git filter-repo` 通常不在 git 自带工具里，用 Python 装。替换表每行 `原文==>替换文`，替换文用**占位符**而不是删空。

## Step 5 复扫与强推

重写后重新盘一遍 Step 1 那五类，确认清零再强推（强推免弹窗的姿势见 `host-gotchas`）。

## 恢复 · 崩溃后顺序不能反

1. **先看 git 状态**，不要先动手修文件
2. 受版本控制的文件 → `git checkout -- <file>` 回到 HEAD
3. **未入库的文件（新建脚本、未提交产出）→ 救不回来，只能重做**

所以：**派完子代理立刻提交。** 崩溃时未提交的工作等于白做。

三条实测：

- `grep -rlP '\x00'` 扫不出被清零的文件（返回空但文件确实全是 NUL）
- 逐文件派生子进程的扫描会被沙箱截断，别用
- 长时间跑的批量任务让它**小步写文件**而不是一次写一个大文件

恢复后**跑一次全量测试**再继续派活，别在损坏状态上继续施工。

子代理留下的类型错误是常见残留——它们常被禁止跑构建，改完测试文件就走。所以验收第一步永远是构建。
