# 证据驱动的结论

**没有数据的判断等于猜测，猜测不能当结论用。** 这条同时约束自己怎么说和对别人产出怎么验收。

## 1. 三种说法要分开

| 说法 | 能不能当结论 | 例子 |
|---|---|---|
| 实测 / 跑过了 | ✅ | 「退 0、8 步全绿、跑完残留 0」 |
| 从代码读出来的 | ✅（要指得出位置） | 「`probe.ts:76` 的 `fs.rm` 抛错会掉进同一个 catch」 |
| 我推测 / 大概是 / 应该是 | ❌ | 「可能是沙箱问题」—— 要变成实测才能写进结论 |

写报告时，凡是不能给出「怎么知道的」的陈述，要么补测，要么标成待验证，要么删掉。

## 2. 报告里要给的东西

- **具体数字**，不是「很多」「少量」「大部分」（「31/87 未登记」比「大量漂移」有用得多）
- **前后对比**（测试数 1043 → 1068，残留 1157 → 0）
- **关键命令输出的关键行**，不是「跑通了」
- **没做到的点**和**不确定项**，显式列出来 —— 藏在结论里会变成别人的坑

## 3. 常见自欺

- **「应该没问题」** → 跑一遍再说
- **「它是这么汇报的」** → 实现方的自述不算证据（见 `subagent-dispatch`：第一步永远是构建）
- **「测试全绿」** → 全绿 ≠ 有保障（见 `fake-test-audit`、`mutation-verify`）
- **「上次验证过」** → 依赖/环境变了，重跑
- **把环境现象当成代码问题**（或反过来）→ 先定位，别先改（见 `windows-sandbox-gotchas`）

## 4. 验收别人的产出时

对每一个「已完成」的声明，问一句：**有什么证据？** 拿不出来的，自己跑一遍。
实测过：汇报「错误码都齐了」而构建有 16 个错 —— 它自己根本没跑通构建。

## 5. 设计清晰度与实现质量分开评估

两件事不要混为一谈：
- 设计清不清晰（方案对不对、边界想没想全）
- 实现好不好（代码质量、测试是否真的守着行为）

一个设计很好但实现没被测试守住的改动，结论要分开写：
「设计成立」「实现有待验证」—— 别因为设计好就默认实现没问题。
