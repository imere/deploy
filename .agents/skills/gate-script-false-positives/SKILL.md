# 门禁脚本的误报治理

## 1. 为什么误报比漏报危险

漏报只是"没抓到"，代码还是对的。
误报会**驱动错误的修改**：

- 人看到红，会去改代码让它变绿；
- 子代理看到红，**一定会**去改代码让它变绿 —— 它不知道那条报错是假的。

实测的一次：JSDoc 门禁因为形参切分不支持泛型，把
`opts: Readonly<Record<string, string>>` 按逗号切成碎片，报出
「形参 `string` 没有 `@param`」。子代理差点为这个不存在的形参写一条注释；
真写了，源码里就会出现一条指向虚无的 `@param string`，后来人看到只会更困惑。

**所以：门禁报红之后的第一件事不是改代码，是确认这条报错是真的。**

## 2. 误报的三个特征（见到就先怀疑脚本）

1. **报出的名字是类型名** —— 形参叫 `string` / `number` / `boolean`，几乎不可能是真形参。
2. **报出的符号在源码里搜不到** —— grep 那个名字，源码里根本没有。
3. **报错集中在某一类签名上** —— 比如所有带泛型的函数都报，不带的不报。
   真缺口不会这么整齐，它跟"这个函数重不重要"相关，跟"签名长什么样"无关。

判据说白了：**真缺口跟语义相关，假缺口跟语法形状相关。**

## 3. 定位脚本 bug 的顺序

不要通读脚本。按这个顺序，三步就能定位：

1. **找报错文案的出处** —— `grep -n "形参" scripts/xxx.mjs`，定位到 `add()` 那一行。
2. **往上找判定条件** —— 谁在往这个 `add()` 里塞数据（通常是 `decl.params` 之类的字段）。
3. **看那个字段是怎么算出来的** —— 解析器函数（如 `splitTop` / `paramNames`）。
   绝大多数误报出在这里：**解析器为了避开某种歧义，做了一个妥协，而妥协有代价**。

实测的那个：`splitTop` 为了不被箭头 `=>` 里的 `>` 误判成括号闭合，选择
**完全不把尖括号当括号**。代价就是泛型里的逗号被当成顶层分隔符。
代码里那两个 `c !== '<'` 就是妥协留下的痕迹 —— 看到这种"刻意排除"的写法，
基本就是误报源。

## 3.1 源码解析器常踩的四类缺陷（实测清单）

写"扫描 TypeScript 源码"的脚本时，这四类几乎必踩：

| 缺陷 | 症状 | 判据修法 |
| --- | --- | --- |
| 切分不认嵌套 | 泛型 `Record<string, string>` 被逗号切成碎片，冒出叫 `string` 的假形参 | 按嵌套深度切分，但**只在类型注解区**认尖括号 |
| 遮罩不认插值 | 模板串里的 `${}` 含同种引号时模板提前"结束"，后面几十行被当字符串吃掉 → 整片符号**看不见**（漏报） | 带栈递归：模板层遇 `${` 进代码层，代码层遇引号递归 |
| 结构误判 | `const X = 1024` 后面没有分号，下一处箭头被算到常量头上，要求常量写 `@param` | 看等号与箭头之间的**整体形状**：只能是 `(...)` 或单个标识符 |
| 递归入口自我排除 | 防环集合预置了起点自身，于是「顺着再导出追一层」永远空转 | 防环交给函数内部的 `seen.add`，起点不要预置 |

共性：**解析器为了避开某种歧义做了妥协，而妥协的代价在另一处爆发。**
看到 `c !== '<'` 这种"刻意排除某个字符"的写法，就在那个函数里找误报源。

## 4. 修的时候：把补偿范围收窄，不要一刀切

错误修法：干脆让尖括号一律参与配平。
那会引入新的误报 —— 默认值里写 `= 1 < 2` 时，`<` 被当成泛型开始，后面的逗号全被吞掉。

正确修法是**限定作用域**：

- 只在**类型注解区**把尖括号当括号（进入时机：顶层冒号）
- 遇到默认值（顶层等号）就退出类型区
- 箭头 `=>` 整体跳过，不要逐字符判

```
if (depth === 0 && c === ':') inType = true
else if (depth === 0 && inType && c === '=') inType = false
```

通用原则：**解析器遇到歧义时，用上下文把作用域收窄，而不是全局开关。**

## 5. 自指陷阱（作者本人踩过）

修"注释里的 glob 字面量会截断解析"这个 bug 时，**在修复的说明注释里写了那个字面量**。
结果自己的注释提前闭合，脚本直接 SyntaxError，而报错指向**下一行**——
看起来像下一行有问题，实际是上一行的注释没闭合。

规则：**修"某种字面量会污染解析"的脚本时，本文件自己的注释里绝不能出现该字面量。**
用「起始标记 / 结束标记」这类代称描述它。

同类陷阱：写检查"代码里不许出现硬编码 IP"的脚本时，脚本里那个 IP 正则本身就是
硬编码 IP —— 它会扫到自己。要么把正则拆开拼，要么把脚本自身排除在扫描范围外。

## 6. 改完必须防回归

只验证"报错消失了"不够，得验证"没把别的判坏"。最小回归集：

1. **已清零的模块仍清零** —— 之前零报错的包/文件，改完还是零。
   这一条能抓住"解析器改动导致整片失明"。
2. **报错总数只减不增** —— 如果修完总数反而涨了，说明引入新误报。
3. **脚本自身能跑** —— 语法错误会以"下一行有问题"的假象出现，别被引偏。

## 7. 门禁的退出码语义

有缺口就非 0 退出是**正确设计**（门禁就该拦住），但要把"有缺口"与"脚本崩了"分开：

- 有缺口：正常输出检查结论，退出码非 0
- 脚本崩了：stderr 有堆栈，且**没有任何正常输出**

验收时别只看退出码，**要先看它有没有输出正常的结论行**。
把崩溃当成"门禁没通过"去修代码，会一路修到不存在的问题上。

## 8. 与子代理并行时的时序

门禁脚本是子代理的验收基准。改脚本会移动它们脚下的地面：

- **改之前**先确认它们还没为误报写出错误注释（`grep` 那个假名字）。
  已经写了就先回滚，再修脚本。
- **改之后**缺口数会变，属于正常；但如果某个代理的目标被你改成了不可达，
  要主动告诉它（否则它会一直重试）。
- 脚本崩溃期间跑的代理会拿到假结果。**崩溃窗口越短越好** ——
  改完立刻自测通过再提交，不要改一半放着。
