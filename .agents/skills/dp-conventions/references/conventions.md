# 本仓约定 · 完整清单

## 清理与回收

- 清理失败**重试一次**（占用多半是瞬时的，杀毒软件在扫刚建的文件），但不无限重试
- 资源链**逆序关闭**，close 必须幂等
- 资源链中任何一跳失败，已建好的全部关掉——这条最容易漏
- 对外暴露残留时用 `leftovers` 列表；干净时结果里不该出现这个键

怎么测：

- 注入一个会抛错的删除函数 → 断言判定仍为成功，且 `leftovers` 记着路径
- 注入一个「第一次抛、第二次成功」的删除函数 → 断言重试后清空
- 资源链注入「第 N 跳失败」→ 断言前 N-1 个都被关掉

## 单一事实来源

- 能抛出的错误码 → 错误码登记表里必须有处置说明
- 登记表里的码不许越堆越多，用「设计期预留」清单放行并定期收紧
- 预留清单里不许留已经实现的码
- 同一份输入喂给两个实现时：都产出 argv 就直接比对；一个产出 argv、一个产出连接对象，就各自导出「目标是谁」的纯函数再比对

看到「注释说 A、实现做 B」时先别急着改注释——先确认哪个是对的，可能是实现错了。

## 凭据

- 凭据内存用完要清理，进程退出前确保不留
- 私钥权限太开会被拒绝，提示里给具体修法（这是正确行为不是 bug）
- 连续认证失败可能触发账户锁定：不要自动反复重试，错误提示里提醒用户
- 区分「可复现的实验环境地址」与「真实凭据」：前者写进文档无妨，后者一个字都不行

测试断言：

- 起进程后检查它的环境，密码字段必须是引用而不是值
- 检查实际 argv（含被包装后的命令）里没有密码
- 把凭据设成显眼字符串，走一遍失败路径，断言错误/告警文本里不含它
- 清理函数重复调用不抛

## git 节奏

- 按依赖顺序推进，每步可独立验证
- 提交信息三段：为什么必须这么改（不这么改会怎样）/ 实测到的事实（有数字优先）/ 取舍（放弃了什么）
- 破坏性操作前先入库
- 推送前：`git status` 干净、待推送提交数与预期一致、远端地址不含凭据
- 评审只看 diff，重点查范围蔓延（顺手改了不该改的）、新增依赖有没有人真的用、注释与实现是否相符

## 接线完整性

- 函数签名里的参数必须每个都被读到。留一个从来不读的参数等于骗调用方
- 导出一个没有任何函数返回的形状，同样是骗——删掉
- 加字段时检查读取方，没有读取方的字段不要加

## 注释与文档

- 不许写「见 xxx.md §N」这类章节号引用，也不许在注释里提文档文件名
- 代码能看出来的不要写；只写「为什么」，且要有依据
- 文档里不要写死盘符、端口、用户名——改成「用 `npm prefix -g` 查」这类可复现说法
