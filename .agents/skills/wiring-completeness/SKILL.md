# 接线完备性：开放 ≠ 接通

在分层的代码里，一个新能力要真正可用，得跨过**三层**：

```
配置层（schema 接受这个字段）
   ↓
推导层（把配置翻译成下层要的参数）
   ↓
消费点（真正把它传出去的那一处）
```

任何一层没接上，用户都能写出合法配置，却拿到一个**静默错误的结果**。
这是最难发现的一类 bug：配置校验通过、类型检查通过、测试全绿。

## 1. 三种漏接的形状（按隐蔽程度排序）

### ① 消费点完全没接 —— 报错还在骗人

最显眼的一种，但报错文案往往仍在描述旧世界。
例：新增了 `hops`（跳板链），而消费点只判断 `ssh === undefined`，
于是配了 `hops` 的用户收到「既没有 ssh 也没有 local」——
**他明明给了目标，只是给的方式是新的**。

排查：报错文案里提到的字段，必须和当前 schema 允许的全部写法一致。
文案漏掉新写法 = 漏接的信号。

### ② 只接了一个消费点 —— 最常漏的一种

同一个配置常常被**两处以上**消费：一处负责「探测目标机状态」，
另一处负责「真正干活的传输/执行」。接了前者漏了后者，表现是：
探测阶段一切正常，执行阶段悄悄退回旧行为（或直连而非走跳板）。

排查：grep 这个字段，**把所有引用点列出来**，逐个确认「它真的被用上了」。
只看改动时想到的那一处是不够的。

### ③ 接了，但没传到下一层 —— 只有测试能抓

推导函数写对了，返回值算得也对，但组装下层参数时忘了带上。
此时所有「推导函数」的单元测试**全绿**，功能却是断的。

排查：测试必须断言「下层收到的参数里含有这个字段」，
而不只是断言推导函数的返回值。见下面「测试怎么写才不算假绿」。

## 2. 推导逻辑必须单一来源

同一个「配置 → 参数」的翻译，若在两个消费点各写一份，
两份就会各自演化：一处加了新写法，另一处没有，
于是**同一个配置在两个地方解释不同**。

这比漏接更难发现，因为两边都能跑通，只是跑出不同结果。

做法：抽一个纯函数当单一来源，两个消费点都调它。
纯函数还有个额外好处——它可以在不碰 IO 的情况下被完整测试。

## 3. 测试怎么写才不算假绿

漏接的三种形状里，只有下面这条断言能抓住 ③：

```ts
// 假绿：只验证推导
const opts = deriveFrom(hostConfig)
assert.deepEqual(opts.host, '10.0.0.7')   // 推导对了，但没人验证它被传下去

// 真断言：验证它到达了下一层
let captured: Options | undefined
await run({ connect: (o) => { captured = o; return fakeConnected() } })
assert.equal(captured?.hops?.length, 2)    // 这才是「接通了」的证据
```

如果被测函数没法注入下层依赖，就给它加一个可选参数
（默认仍是真实实现）—— 这是为了让「接通」这件事可被断言，值得开这个口子。

同理，每个消费点都要有自己那条断言。只测推导函数、
再用一句「消费点调用了它」糊过去，等于没测。

## 4. 收尾检查清单

- [ ] schema 接受的所有写法，**报错文案**里都提到了吗（形状 ①）
- [ ] grep 字段名，列全引用点，**每一处**都用上了吗（形状 ②）
- [ ] 有没有一条断言证明它**传到了下一层**（形状 ③）
- [ ] 推导逻辑是不是只有一份（§2）
- [ ] 两个消费点给同一份配置，产出一致吗（见 `shared-input-semantics`）
