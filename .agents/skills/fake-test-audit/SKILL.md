# 假测试与假门禁审查

## 步骤

1. 加载 `references/review-checklist.md`，那是完整的信号清单与判定口径
2. 通读被测代码，先理解它要做什么再评判
3. 逐条套清单。每条命中都要给 `文件:行号` 和为什么；拿不准就标「可疑，待人工判」
4. 按严重度分组输出：`error` 必须修 / `warning` 应该修 / `info` 可考虑
5. 给 1-10 分与理由，最后列三条最有价值的改进

## 三条硬规矩

- **不许乱扣帽子，也不许为了显得干净而放行。**「没发现凑数」必须是查过之后的结论，要写明查了哪些、怎么排除的。不查而说没发现，等于没查
- **发现真问题不要自己顺手改测试断言**，那是另一个任务的授权范围。列出来交给负责人
- **误报比漏报危险。** 下游（人或子代理）会为了消灭一个不存在的问题去改对的代码。见到可疑报错先怀疑脚本

## 门禁报错可疑时的三个特征

见到任一条，先怀疑是脚本有 bug 而不是代码有问题：

1. 报出的名字是类型名（`string` / `number` / `boolean`）——几乎不可能是真形参
2. 报出的符号在源码里 grep 不到
3. 报错集中在某一类签名上（比如所有带泛型的函数都报，不带的不报）

定位顺序：找报错文案的出处 → 往上找谁在往里塞数据 → 看那个字段怎么算出来的（通常是解析器函数）。

## 修完防回归

- 之前零报错的包/文件，改完还是零
- 报错总数只减不增——修完反而涨说明引入了新误报
- 脚本自身能跑：语法错误会以「下一行有问题」的假象出现，别被引偏

## 终局只能靠变异

静态排查有天花板。要证明一条测试真的守着某个行为，只有变异验证能做到——撤掉修复看测试变不变红。见 `mutation-verify`。
