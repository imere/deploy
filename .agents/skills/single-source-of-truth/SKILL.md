# 单一来源：让「两处事实」不可能共存

同一件事只要在两处写了，就会漂。治理的目标不是「改一致」，
而是**让它结构上不可能不一致**。

## 1. 常量上收到共享层

症状：目录命名、默认值、候选表在多个包里各写一份字面量
（`releases/` / `current` / `.incoming` 散落各处）。

修法：提到共享契约包，所有包引用它。**驱动偏好表这类「决策表」尤其要收口** ——
多个包各自列一份顺序，迟早出现「A 包认为先试 X、B 包认为先试 Y」。

收口后要注意：不同场景需要的候选可能不同（远端要追加临时目录），
用「共享基线 + 各侧追加」的组合，而不是各自从头写。

## 2. 类型由数组派生，而不是反过来

```ts
export const ERROR_CODES = ['DP.A', 'DP.B'] as const
export type ErrorCode = (typeof ERROR_CODES)[number]
```

好处：「这个码在不在册」变成**可自动校验**的事，
而不是靠人维护两份清单（一份类型、一份文档）。
新增码忘记登记 → 编译不过 / 测试变红。

反过来（先写类型联合、再手写文档表）必然漂移。

## 3. 定期清空死码

扫描「声明了但全仓没人抛出」的码，直接删。实测一次删掉 10 个。
留着它们会让文档表越来越长，读者分不清哪些是真会遇到的。

## 4. 用棘轮测试钉住文档

文档表与代码清单的对应关系写成测试（详见 `doc-truthfulness` 的「用测试把文档钉住」）：
- 能抛出的码 → 必须在文档里有处置说明
- 文档里的码不许越堆越多（用「设计期预留」清单放行，定期收紧）
- 预留清单里不许留已实现的码

## 5. 命名迁移要一次做完

历史名与新名并存（如 `CONFIG_INVALID` 与 `DP.CONFIG.INVALID`）时：
退出码映射可能两种都认、测试也全绿，但**帮助文本与文档会自相矛盾**，
用户看到两个名字不知道该查哪个。

做法：全仓替换（注意形态：裸写 / 反引号 / 引号包裹都要覆盖），
清掉重复的枚举条目，注释里写明「历史名已废弃」，然后跑测试确认没漏。

**替换后必做**：查文档里是否还有旧名、以及是否有被替换规则误伤的地方
（比如类型示例里本来就写着一批示意性的名字）。
