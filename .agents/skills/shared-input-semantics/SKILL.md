# 同一份输入，两种解释

一个字段只要被**两个以上实现**消费，就埋着一类特殊风险：
两个实现都能跑通，各自测试也都是绿的，**只有它们跑出不同结果时**问题才显形。

典型形状：A 实现把字段当成「全部都是 X」，B 实现把字段当成「最后一个是 Y」。
用户写一份配置，换个驱动就连到了另一个地方 —— 而两边都没有任何报错。

## 1. 为什么各自的测试抓不到

每个实现的测试都是**拿自己的假想去喂自己的实现**：

```
test('A 的行为') → 用 A 的语义造输入 → A 产出符合 A 语义 → 绿
test('B 的行为') → 用 B 的语义造输入 → B 产出符合 B 语义 → 绿
```

两边都对，因为断言的是各自的实现，不是**它们应当达成的共识**。
缺的是一条「同一份输入，两个实现产出的东西可比对」的对照断言。

## 2. 对照测试怎么写

给两个实现喂**完全相同**的一份输入，断言产出的**可比对部分**一致：

- 都产出 argv → 比对「最终连到哪个 host」
- 一个产出 argv、一个产出连接对象 → 各自导出一个「目标是谁」的纯函数再比对
- 比对不上就说明语义分叉了，此时**不要**去改测试迁就实现

关键：比对的那个量必须是**用户能感知的结果**（连到哪台机器、写到哪个路径），
而不是内部中间结构 —— 中间结构不同常常是合理的。

## 3. 冲突了，谁对？用约束反推，不要投票

两个实现说法不一致时，不要靠「哪个写得更早 / 哪个代码更多」来判。
找**配置层的约束**，让它替你做决定。实际用过且有效的三种：

| 约束 | 能推出什么 |
|---|---|
| 两字段互斥（给了 A 就不能给 B） | 那么 B 必须**自带完整信息**，不能指望还有个 A 补位 |
| 某字段必填 | 它的来源必须确定，不能依赖「另一处可能会填」 |
| 类型上可选但语义上必需 | 说明消费方需要自己兜底，兜底方式也必须两处一致 |

例：`ssh` 与 `hops` 互斥 → 只写 `hops` 时目标机从哪来？
只能来自 `hops` 内部 → **最后一跳就是目标机**。
这个结论不需要猜，是互斥约束逼出来的。

推导出语义后，**用这个语义去判两个实现谁错了**，而不是反过来让实现定义语义。

## 4. 语义要写在单一来源里

定下来的语义必须落在**一处**，并且是那个最不容易被绕过的类型定义或纯函数：
写在消费它的某个实现里，另一个实现就看不见（它不会去读别人的文件）。

做法：把语义写进共享的类型定义 / 纯函数的注释里，
各实现的注释指向它 —— 而不是各自抄一句「我认为它是 XX」。

## 5. 注释漂移是这类 bug 最好的报警器

讽刺的是，发现语义分叉往往靠**注释**：
一个文件写着「最后一跳是目标机」，另一个文件的实现却不是这么做的。

所以：
- 改实现时，检查描述这段语义的注释还在不在理
- 反过来，看到「注释说 A、实现做 B」，先别急着改注释 ——
  **先确认是注释过期还是实现错了**，判据就是上面第 3 节的约束反推
- 禁止写「见 xxx.md §N」这类章节号引用作为依据：章节号会漂移，
  读代码的人手边也没有文档。依据要么就地把事实写清，要么指向代码里的函数／常量

## 6. 收尾检查清单

- [ ] 同一份输入喂给两个实现，用户可感知的结果一致吗
- [ ] 语义写在共享的单一来源里了吗（不是各自抄一份）
- [ ] 冲突时用约束推过语义了吗（不是靠猜）
- [ ] 两边描述语义的注释，和各自的实现还对得上吗
