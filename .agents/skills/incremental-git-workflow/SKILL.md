# 渐进式 git 工作流

## 1. 按依赖顺序推进，每步可独立验证

把任务拆成「每一步都能单独编译、单独测试」的序列，做完一步提交一步。
不要攒一大堆改动到最后一次提交 —— 出问题分不清是哪一步引入的。

拆分的判断标准：**这一步能不能单独说清楚「改了什么、为什么」**。
说不清就说明它里面有两件事。

## 2. 提交信息写「为什么」，不是「改了什么」

「改了什么」看 diff 就知道，不需要写进提交信息。要写的是：
- **为什么必须这么改**（不这么改会怎样）
- **实测到的事实**（有数字优先）
- **取舍**：放弃了什么、为什么

反面：`fix bug` / `update` / `优化代码`。正面：

```
fix(local): 写权限探测不再被自己的清理失败推翻，残留也不再静默

三件事原本被塞进同一个 try：建文件 / 删文件 / 判可写。于是删除一抛错就同时导致
目录被判「不可写」、临时文件留在原地、错误被整个吞掉。

实测后果：探测垃圾攒到上千个，之后每次探测都被判不可写，本机所有候选目录同时死掉。
```

## 3. 破坏性操作前先入库

删除文件、大范围重构前**先提交一次**，留一个回滚点。
即使只有本地提交，也比「改坏了没处回」强。

## 4. 后续只审 diff

不要重读整个文件，看 `git diff` 就够了，而且更容易发现问题：
重读会跳过「看起来本来就该这样」的地方，diff 强制你看变化本身。

审 diff 时重点看：
- 有没有**顺手改了不该改的**（范围蔓延是子代理和急切状态下最常见的毛病）
- 新增的依赖/字段**有没有人真的用**
- 注释与实现是否相符

## 5. 推送前

- 工作区干净（`git status` 无异常）
- 确认待推送的提交数与预期一致
- 远端地址**不含凭据**（凭据用环境变量临时注入，推完恢复）
- 见 `git-noninteractive`：绝不弹窗
