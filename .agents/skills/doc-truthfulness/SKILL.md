# 文档真实性审计

文档失真分两类，都要治：
1. **声称已落地、实际不存在**（最危险 —— 用户照着做会踩空）
2. **含糊注水**（读了没信息量，还占篇幅）

## 1. 查「文档说有、代码没有」

按这个顺序扫：

```bash
# 文档里声称已实现的
grep -rn "已实现\|已支持\|已落地\|已接入\|已配置" -- '*.md'
# 文档里承诺还没做的（确认标注是否还准确）
grep -rn "尚未实现\|待实现\|未接线" -- '*.md'
# 工程化选型（最容易照抄规划）
grep -rn "测试框架\|构建工具\|包管理器\|linter\|CI\|发版工具" -- '*.md'
```

**逐条回源码核实**，不要凭印象。实测查出三处硬伤：

- 工程化整表是照抄的规划：写的 Node 版本、构建工具、测试框架、linter、发版工具、CI
  **六项全部不存在**（实际是另一套）。→ 拆成「当前实际」+「尚未落地」两张表。
- 配置文档把一批字段**当成已支持在写**，而 schema 里根本没有（`hops`、`crypto`、
  `knownHosts`、`timeouts`、docker 的 `build`/`registry`）。→ 逐条标成未落地，
  并补上 schema 里**真实存在**的写法（用户得知道能写什么）。
- 里程碑表没有状态列，读者分不清哪些跑通了。→ 加状态列，每格写明**差在哪条判据**。

核实工具链事实时，直接读配置（`package.json` 的 scripts、有无配置文件、有无 CI 目录），
别读文档对文档。

## 2. 状态标注的写法

不要只写「未实现」，要写**差在哪**：

| 标记 | 含义 |
|---|---|
| ✅ | 有测试守着，且判据已跑过 |
| ⚠️ | 代码写了，但关键判据没验（要写明差哪条：真机没跑 / 只支持其中一种模式 / 配置层未开放） |
| ❌ | 没有 |

**⚠️ 与 ❌ 的区别必须写清楚**，否则读者会把「写了代码」当成「能用」。

## 3. 用测试把文档钉住（棘轮）

文档漂移靠自觉是守不住的，写一条测试：

- 代码里能抛出的错误码 → 必须在故障分类文档里有处置说明
- 文档里出现的码 → 不许越堆越多（用一份「设计期预留」清单放行，并定期收紧）
- 预留清单里不许留**已经实现**的码（实现了就从预留里挪出去）

这类测试实测抓到过：改文档时引入了两个文档里没登记过的码名，当场变红。
**替换时记得按「实际出现的字符串」写规则** —— 裸写、反引号包裹、带引号是三种形态，
只按一种匹配必漏（实测漏了两处，跑了第二轮才干净）。

## 4. 含糊注水表述

典型是把**作者自己的机器**写成「本机」「本地环境」「我们这边」—— 换个读者就不成立。

**先分类再改，别一刀切。** 实测「本机」117 行里，多数是**合法领域术语**
（「本机 rsync」「本机不落地」「本机目标」都是相对远端目标的准确语义），
真正要改的是指作者开发机的那批（约 30 处）。改完 117 → 86。
派发子代理做时**必须给反例清单**，否则它会一律改掉。

套话词扫描（命中就删）：`需要注意的是` `值得一提的是` `众所周知` `显而易见`
`简单来说` `综上所述` `毫无疑问` `显然` `其实`。

另一类是**声称「实测」却给不出依据**，或编造无法核实的机制。
实测抓到子代理把「装不上」改成「某操作系统沙箱内 spawn 失败，errno X」——
这是它编的、无法核实，改回保守说法（只写事实：装不上）。

## 5. 子代理写文档时的额外风险

- 它会把规划当现状抄（写「已接入 X」因为设计文档里写了）
- 它会编造机制来解释现象 → 凡「因为某某内部原因」都要能指出依据，否则删
- 它分不清领域术语与含糊指代 → 给正反例清单
