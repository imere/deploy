# 清理逻辑：不静默、不推翻、可注入

## 1. 反模式：把「做 / 清 / 判」塞进同一个 try

```ts
// ❌ 实测事故
try {
  await fs.writeFile(probe, '')      // ① 建文件（这一步成功 = 目录可写）
  await fs.rm(probe)                 // ② 清理
  canWrite[dir] = true               // ③ 判定
} catch {
  canWrite[dir] = false              // ② 一抛错就跳到这里
}
```

三件事被一个 `try` 包住，② 抛错时同时发生：
- **判定被推翻**：① 明明成功了（这本身就是「能写」的实证），却因为清理失败判成不可写
- **残留留在原地**：临时文件没人管
- **错误被吞掉**：`catch` 里没有任何日志或返回值，事后完全查不到原因

实测后果：探测垃圾在候选目录攒到上千个，攒多之后**每次探测都被判不可写**，
所有候选同时失效，功能在本机彻底跑不了，而日志里没有任何东西指得到原因。

## 2. 正确姿势

- **判定只看「已经成功的实证」**：文件建成功了就说明可写，与后面清不清理无关
- **清理单独做**，失败进一个 `leftovers` 列表交出去，不静默、不改写判定
- **清理失败重试一次**：占用多半是瞬时的（杀毒软件在扫刚建的文件），但不无限重试
- **删除动作可注入**：否则「删不掉」这条路径在真机上根本没法测

```ts
const created = await createProbe(dir)
canWrite[dir] = created                       // 判定与清理无关
if (created && !(await removeOnceWithRetry(probe, remove))) {
  leftovers.push(probe)                       // 留痕，交出去
}
```

## 3. 对外暴露「残留」时的约定

用**键不存在**区分「回收干净」与「根本没探过」：
只在真有残留时才往结果里放 `leftovers` 键。调用方靠这个区分两种「没有」，
否则「全清干净」和「压根没跑」长得一样。

## 4. 资源链的清理

连接、锁、租约这类成链的资源：
- **逆序关闭**
- **幂等**（重复 close 不报错）
- **任何一跳失败，已建好的全部关掉** —— 这是最容易漏的一条，
  漏了就在远端留一堆孤儿连接/锁，且测试几乎不会发现（测试只看「报错了」）

## 5. 怎么测

- 注入一个**会抛错**的删除函数，断言：判定仍为「成功」+ `leftovers` 记着路径
- 注入一个**第一次抛、第二次成功**的删除函数，断言：重试后清空、`leftovers` 为空
- 断言「干净时结果里没有 leftovers 键」
- 对资源链：注入「第 N 跳失败」，断言前 N-1 个都被关掉了
