# 自动化程序的三条铁律

这类程序一旦在无人值守时挂起或猜错，代价极高（CI 永久卡住、把预发发到生产）。
三条铁律都是**硬约束**，不是风格建议。

## 铁律 1：永不交互

任何路径都不许等人类输入。

- **不弹凭据窗口**：GUI 凭据助手会挂几分钟且无人去点（见 `git-noninteractive`）
- **不等 stdin**：远端命令一旦等待输入，程序就永久挂起。
  子进程的 stdout/stderr 要**嗅探交互式提示**（`Password:`、`[sudo] password`、
  `(yes/no)`、shell 提示符等），命中立刻断链并报结构化错误，而不是等它回完
- **所有子进程/连接必须带超时**，没超时的调用就是潜在的永久挂起
- **宁可报错也不要硬跑**：明知会等输入还跑，等于把挂起当成可接受结果
- **CI 里的工具链也要检查会不会问**：以为「装依赖」这一步不会交互是错的 ——
  `corepack enable pnpm` 默认会在 TTY 里问「是否下载该版本」，无人值守下就是一次挂起。
  凡是「按需下载 / 首次使用要确认」的工具，都要显式关掉提示再进自动化
- **版本固定别顺手写在 `packageManager` 字段里**：实测它一加，包管理器就把**自己**
  写进 lockfile（+158 行各平台二进制）。而 CI 跑 `--frozen-lockfile` 时，不提交 lockfile
  就红、提交就为「固定一个版本」平白多一份供应链面。改成镜像里全局预装，版本仍只写一处

判断标准：把一个命令拿给人看，如果它会「停下来问一句」，就不能进自动化链路。

## 铁律 2：能力实证，不猜

能不能用某个能力，**跑一次看结果**，不靠版本号、路径存在性、配置文件猜。

- 工具在不在 → 执行 `--version` 或等效探测，看返回码
- 目录能不能写 → 真建一个文件试试（`cleanup-not-silent` 讲了怎么不留下垃圾）
- 协商手段（压缩/传输/转发方式）→ 逐种试，记录每种为什么不行

**降级要显式且留痕**：多种手段都不通时，报错里列清「试过哪些、各自为什么失败」，
不写「不支持」三个字。用户要靠这个决定下一步。

## 铁律 3：歧义靠拒绝

遇到有多种合理解释的输入，**报错并列出候选与排除办法**，不猜一个默认值继续跑。

典型场景：
- 多个环境/配置文件，没指定用哪个 → 报错（默认挑第一个 = 把预发发到生产的入口）
- 同一件事两处配置矛盾（串里端口 vs 端口字段）→ 报错（取错了就连到另一台机器）
- 某个必填项缺失 → 报错并指出**具体路径**（`hosts.*.ssh.hops[1].auth`，
  而不是「认证配置有误」）
- 列表超长 → 报错而不是静默截断（截断会让人以为看全了）

**「默认值」不算猜**：schema 里明确声明的默认值可以从 schema 取，
但**不要在实现里另存一份**（见 `single-source-of-truth`）。

区分两种「没有」很重要：
「用户没写」和「用户写了但等于默认值」是两件事，用 `undefined` 与默认值的区别来判断，
不要靠比较值相等 —— 值相等时你分不出来。

## 配套：错误要能指导下一步

结构化错误至少带三样：机器可读的**码**、能定位到的**路径**、给人看的**下一步建议**。
错误消息里**绝不能出现凭据明文**（见 `secret-hygiene`）。
