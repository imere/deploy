# 安全模型

> 一句话：**部署工具是拿root 权限往生产机器上写东西的程序，它的默认行为必须比它的环境变量重命名时要保守。**

配套：[`transport.md`](./transport.md) 讲连接怎么建，[`config.md`](./config.md) 讲这些策略怎么配。

---

## 1. 威胁模型：先说清楚防谁

| 威胁 | 攻击者 | 防御手段 |
| --- | --- | --- |
| 凭据泄露 | 能读本机文件 / 同机其他用户 / CI 日志 | secretRef、环境变量单行传递、统一脱敏、不落盘 |
| 中间人 | 网络上的攻击者（含未来的量子敌手） | 严格的主机密钥策略 + 抗量子密钥协商 |
| 命令注入 | 配置文件里被注入、路径含空格或恶意字符 | 一律 argv、`quote()` 唯一出口、属性测试 |
| 路径穿越 | 恶意/错误的远端路径 `../../etc` | plan 期校验所有远端路径落在 `release.root` 下 |
| 符号链接攻击 | 源码树里藏一个指向 `/etc/shadow` 的软链接 | 传输前扫描源树，拒绝指向源根之外的符号链接 |
| 供应链 | 恶意依赖 | pnpm 构建脚本白名单、锁文件、跳过可选原生依赖 |
| 破坏性误操作 | 自己 | `--delete` / 覆盖非托管文件 / prune 旧版本全部需显式开关 |
| 审计缺失 | 事后复盘 | 每次部署留 trace，记录谁、何时、哪台、什么版本、用了什么算法 |

不防御的东西也写明白：**不防御已有 root 权限的攻击者**（他能改 sshd 配置，我们无能为力），也不假设配置文件可信到可以执行任意回调 —— `hooks` 命令要是被注入，注入者已经能写代码了。

## 2. 抗量子密钥协商（PQC）

### 事实基线

- OpenSSH 从 **9.0**（2022）起默认提供 `sntrup761x25519-sha512`（NTRU Prime 混合）
- OpenSSH **9.9**（2024）加入 `mlkem768x25519-sha256`，**10.0**（2025）起作为默认密钥协商
- OpenSSH **10.1** 起对非抗量子协商发出 `WarnWeakCrypto` 警告
- ML-KEM 是 NIST **FIPS 203**（2024.8）标准化的算法
- 实测 ssh 为 **OpenSSH 10.3p1**，支持上述所有；Node 门槛为 **≥ 24**

这些算法都是**混合构造**：会话密钥由经典交换与后量子封装两者共同派生，**任意一半没被攻破，会话就还安全**。这也是为什么可以放心地默认开启。

### 三条策略

```yaml
crypto:
  kexPolicy: pq-preferred    # pq-preferred（默认） | pq-required | compat
  warnWeakCrypto: true       # 对非抗量子连接发警告
  algorithms:                # 可选：完全显式指定
    kex:    ['mlkem768x25519-sha256', 'sntrup761x25519-sha512', 'curve25519-sha256']
    cipher: ['chacha20-poly1305@openssh.com', 'aes256-gcm@openssh.com', 'aes128-gcm@openssh.com']
    mac:    ['hmac-sha2-512-etm@openssh.com', 'hmac-sha2-256-etm@openssh.com']
    serverHostKey: ['ssh-ed25519', 'rsa-sha2-512', 'rsa-sha2-256']
```

| 策略 | 行为 | 用在哪 |
| --- | --- | --- |
| `pq-preferred` | 优先协商 PQ 混合算法；对方不支持时降级到经典算法并**发警告** | **默认**。可用性优先，不甩手降级 |
| `pq-required` | 必须协商出 PQ 算法，否则**连接失败** | 合规要求严格的环境；明确地失败比静默接受弱算法好 |
| `compat` | 不干预，用 ssh2 默认列表 | 只有遇到连不上、且确认对方是老设备的临时退路 |

### 必须处理的两件事

**(1) 逐跳协商，链的安全性 = 最弱的一段。**

这是多跳场景里最容易漏的一条：

```mermaid
flowchart LR
    ME["本机<br/>✅ 支持 ML-KEM"]
    H1["跳板机<br/>OpenSSH 7.4<br/>❌ 只有经典算法"]
    TG["目标机<br/>✅ 支持 ML-KEM"]
    ME <-->|"段①: 协商出 curve25519<br/>（被拖下来）"| H1
    H1 <-->|"段②: ML-KEM"| TG
    classDef weak fill:#450a0a,stroke:#f87171,color:#fee2e2
    classDef ok fill:#134e4a,stroke:#2dd4bf,color:#ccfbf1
    class H1 weak
    class ME,TG ok
```

**即使两端都支持抗量子，中间跳板会把整条链拖回经典算法。** 「现在窃取、以后解密」的攻击自己不需要攻破整条链 —— 只要拿到**任何一段**的握手和密文就能存起来。

所以：

- crypto 策略在 **每一跳独立应用**
- `dp check --crypto` 输出每跳的协商结果表格，并注明是否 PQ
- `pq-required` 在**任意一跳**不满足时整次失败，而不是只在最后一跳检查

**(2) Node 版本会决定能不能用 ML-KEM。**

纯 ML-KEM 依赖 Node 的 crypto 邮箱提供 ML-KEM 支持，而相关实现要到 **Node ≥ 24.7.0** 才有底层支持。由此产生一条明确的版本门禁：

| Node | 能用 | 建议 |
| --- | --- | --- |
| ≥ 24.7 | ML-KEM 混合（若客户端库支持）+ sntrup761 | **推荐**，`.nvmrc` 写 24 |
| < 24.7 | 退到 `sntrup761x25519-sha512`（若库支持）或经典 curve25519 | 明确告知用户「本机 Node 版本限制了抗量子选项」 |

> ⚠️ **P1 阶段必须实测的一件事**：用最小脚本验证当前 `ssh2`（实测最新为 **1.17.0**）在 Node 22 与 Node 24 下分别能协商出什么 kex —— 直接连接 OpenSSH 10.3 服务端观察结果。这会明确 `pq-required` 到底能不能落地，以及要不要把 Node 提到 24。**设计阶段不下结论，动手第一步就把它测实。**

### 主机密钥与算法偏好

- 主机密钥策略：`strict`（默认，指纹需预置或已在 `~/.ssh/known_hosts`）/ `tofu`（首次信任并记录，之后变更多报错）/ `none`（必须配 `allowInsecure: true`）
- 密钥类型偏好 `ssh-ed25519` 优先，其次 RSA-SHA2，**禁用 `ssh-rsa`(SHA-1) 与 `ssh-dss`**
- 从不动武 forwarding：默认**不开启 agent forwarding**（把钥匙交给中间跳板），需要时必须逐跳显式打开
- PQC 签名算法目前在 SSH 领域仍属实验阶段（如 mldsa 混合 edible25519 composite），**默认关闭**，只留一个显式开关给愿意趟坑的人

## 3. 凭据处理

| 规则 | 做法 |
| --- | --- |
| 配置里不放明文 | `passwordRef: env:X` / `file:` / `prompt:` / `cmd:` |
| 不进命令行 | `sudo -S` 从 stdin 读密码，不写成 `echo pw \| sudo` |
| 不进环境变量 | 传给子进程的只有 IPC token，不含凭据本体 |
| 不落临时文件 | 私钥从内存/buffer 直接给 ssh2 |
| 统一脱敏 | Logger 的出口统一 scrub，**禁止单点 `console.log`** |
| 支持审计 | `--audit` 报告配置里有没有明文凭据，CI 里可以当门禁 |

`prompt:` 在没有 TTY 的非交互环境要**明确报错**，不要卡住等待。

## 4. 命令注入与路径安全

- **所有命令走 argv**，禁止拼字符串跑 shell。只有必须过一层 shell 的场景（`su -c`）才用 `quote()`，且它是唯一出口
- `quote()` 配**属性测试**：随机生成含空格、引号、`$`、反引号、换行的串 → quote → 反解析 → 必须等于原串
- 远端路径在 plan 期校验：`..`、绝对路径、符号链接逃逸一律拒绝
- 源树扫描：拒绝指向源根目录之外的符号链接（`rsyn c` 的 `--safe-links` 语义对我们是不够的，因为我们要自己的 contract）

## 5. 传输完整性

不管用哪种传输策略，都做一遍验证：

| 策略 | 校验方式 |
| --- | --- |
| rsync / tar-ssh | 传完后跑校验：远端列出文件清单 + 大小/MTIME，必要时抽样 sha256 |
| sftp | 同上，且自己实现 size+mtime 比对 |
| 跨机器集群 | 各主机**独立校验**，不允许「一台成功就当全体成功」 |

同时在 plan 里对 release 写一个 `.dp/checksums.txt`，回滚时就地用它验证旧版本是否还完整。

## 6. 最小权限与审计

- 默认不追加 `-E`（不保留 sudo 前的环境变量）
- `--audit` 输出建议的 **sudoers drop-in**（把命令收敛到部署必需的几条），但**绝不自动写 `/etc/sudoers.d/`**
- 每次部署留 `$XDG_STATE_HOME/dp/trace/<deployId>.json`（system 布局下 `/var/lib/dp/trace/`）：操作者、时间、来源 commit、目标主机、每步耗时、协商出的 crypto、结果 —— 不含机密
- Exit code 要能区分用途：成功 0、部署失败 1、**校验失败且已回滚 2**、配置错 3、环境缺依赖 4。CI 才好用

**前提：`become` 是可选的，root 不一定存在。** 普通账号 + sudo 是常态，纯普通用户也是受支持的一等公民。完整模型见 `privilege.md`，下面只写权限部分。

### 6.1 目标机状态目录的权限模型

状态目录承接 journal、租约锁、当前版本指针 —— 是我们**在目标机上唯一长期持有的可变状态**。它的**位置随布局变**，权限必须显式定义，不能靠 umask 运气：

| 位置（system 布局 / user 布局） | owner | mode | 理由 |
|---|---|---|---|
| `/var/lib/dp/` ／ `$XDG_STATE_HOME/dp/` | **布局所有者** | `0750` | 状态默认不含服务身份的读需求 |
| `…/state/<project>/` | 同上 | `0700` | journal 含主机名/路径/部署轨迹，不应对外可读 |
| `…/state/<project>/current`（导出子集） | 同上 | `0644` | 服务身份需要读的唯一一份，单独导出 |
| 临时目录 | 部署身份 | `0700` | 与 一致 |

**目录链同样要逐层校验**：每一级的 owner 必须等于**布局所有者**且不能被其他身份写，否则租约锁可被伪造（攻击者写一个假锁就能让所有部署永久阻塞 —— 这是可用性攻击，不只是权限问题）。

### 6.2 带外执行面：代码与数据必须分离

这是部署工具特有的一个提权陷阱，值得单独列为一条原则：

> **任何会被定时执行的东西，其代码路径必须完全不可被部署身份写入；它与可变数据必须位于不同的信任域。**

注意这里写的是"定时执行"而非"被 root 定时执行" —— 原则与是否为 root **无关**，取决于"执行者是谁"与"谁能写"。两个域的具体形态随布局而定（各布局下的两个域见 `failures.md`）。要点复述：

- 代码 `0755` 且归布局所有者，数据可写 —— **绝不放在同一目录**
- 安装前逐层校验目录链，`DP.SEC.RESCUE_UNSAFE_PATH` 是**拒绝**而非警告
- 脚本内嵌 sha256 自校验
- 状态文件取出的值**只作引用过的参数**，过 allowlist，**永不 `eval`**
- 默认不安装；`dp host prepare --with-rescue` 显式开启

推论：**「让普通用户能部署」与「让特权身份定时执行脚本」这两个需求，在同一路径上不可调和。** 遇到时二选一 —— 要么放弃带外救援（默认，且在 user 布局下本来就不可靠），要么让部署与执行都走同一特权身份并接受审计要求。

**绝不做的事**：碰到权限不够就 `chmod` / `chown` 系统目录，或自动改 `/etc/sudoers.d/`。权限不够就是不够 —— 报错、给建议、让用户自己决定。

## 7. 供应链

- **pnpm 构建脚本白名单**在 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 里显式列出 —— pnpm 10+ 默认阻断全部构建脚本
- `ssh2@1.17.0` 的可选依赖 `cpu-features`、`nan` 需要本地编译。**建议跳过可选依赖**（它们只用于按 CPU 特性排 cipher 优先级），这样：
  - Windows 上不必准备原生编译工具链
  - 减少不可复现的构建差异
  - 代价仅是默认 cipher 顺序不是最优 —— 但我们本来就会显式指定 cipher 列表，所以这个代价接近于零
- 锁文件必须进版本库，CI 用 `--frozen-lockfile`

## 8. 一条总结性原则

**默认安全，显式不安全。** 需要补课的功能（自动信任主机指纹、允许 ssh-rsa、跳过 PQC、agent forwarding、 instruct delete、覆盖非托管文件）都必须逐个显式打开，而且**打开时要在日志里说明代价**。它们分布在配置各处不打紧，但要能从 `dp check --security` 一次性列出：「本次会话偏离了这些安全默认值」。
